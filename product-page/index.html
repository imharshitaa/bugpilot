Overview

What's actually implemented

Every capability below maps to real code in the repository, not a roadmap item. See the README's "What's aspirational" section for the honest list of what isn't there yet (e.g. exploit/test run the same module set as scan with different output, rather than a distinct exploitation engine).

Scope & authorization guard

Every target host is checked against config/scope.txt or an explicit --authorize/interactive confirmation before any request is sent. Unauthorized targets raise AuthorizationError and exit non-zero.

SSRF protection

Resolves every hostname and rejects private/loopback/link-local/metadata/multicast/reserved addresses — including on every redirect hop, not just the initial request.

Confidence-scored detection

Findings carry a per-module confidence score; anything below min_confidence (default 0.6) is filtered from the default report, so heuristic signals don't drown out confirmed behavior.

Plugin-based module system

17 built-in detectors loaded through core/plugin_manager.py, enabled/disabled via config/modules.yaml, each contributing a uniform finding shape.

Risk scoring & dedup

Findings are scored from severity, confidence, evidence length, and endpoint sensitivity, then deduplicated by type/endpoint/payload before reporting.

Differential scanning

core/diff_scan.py compares a run against a baseline findings.json so CI can flag newly introduced issues.

Multi-format reporting

Markdown, JSON, and SARIF output per run under reports/output/run_<timestamp>/ — SARIF feeds straight into GitHub code scanning.

Real CI gate

.github/workflows/ci.yml runs the full pytest suite, then a real authorized headless scan against the bundled lab app with --fail-on-findings.

Bundled vulnerable lab app

labapp/ is a small Flask app with intentional, well-understood vulnerabilities — a safe local target for trying every command with no external traffic.

Vulnerability scanning

17 detection modules, one finding shape

Every module is a plugin that returns a list of findings against discovered endpoints — enabled centrally in config/modules.yaml. No module reports a finding from a keyword match alone; each requires an observed behavioral difference (reflected payload, differing status or body, redirect to an attacker-controlled host, a missing header, etc.).

Authorization & scope

BugPilot refuses to request a target it isn't authorized for

core/scope.py is the single gate every target passes through before any HTTP request is made:

  • Hosts listed in config/scope.txt are pre-authorized.
  • Any other host requires an explicit --authorize flag (required in headless/CI mode), or a y answer to an interactive confirmation prompt.
  • Unauthorized targets raise AuthorizationError and the command exits non-zero — before any network request is made.
  • Once a host is authorized, the SSRF guard still allows private/loopback addresses only for that host — this is what lets you scan 127.0.0.1/the bundled lab app locally while still blocking an unauthorized target's redirect from pivoting to internal/metadata addresses.

Try it against the bundled lab app — safe, local, no external traffic:

python -m labapp.app &
bugpilot scan http://127.0.0.1:5000 --authorize

core/scope.py — authorization decision

for host in unauthorized:
    if confirm:                    # --authorize
        authorized.add(host)
        continue
    if interactive:                 # y/N prompt
        answer = input(
            f"[?] '{host}' is not in "
            f"config/scope.txt. Confirm "
            f"you are authorized (y/N): "
        )
        if answer.lower() in ("y", "yes"):
            authorized.add(host)
            continue
        raise AuthorizationError(
            f"Authorization declined for "
            f"host: {host}"
        )
    raise AuthorizationError(
        f"Host '{host}' is not authorized."
    )

SSRF protection & confidence

Fail-closed network guard, calibrated detection confidence

core/ssrf_guard.py is the single place that decides whether a URL is safe for the scanner to request. It is intentionally conservative — anything it cannot resolve or classify is treated as unsafe:

  • Resolves the hostname via socket.getaddrinfo and inspects every returned address.
  • Rejects private, loopback, link-local, multicast, reserved, and unspecified IP ranges.
  • Re-validated on every redirect hop, not just the initial request — core/utils.py follows redirects manually so each hop passes back through the guard.
  • Authorized hosts (scope-listed or --authorize'd) may still resolve to private addresses, so the bundled lab app keeps working.
  • DNS failures, unparseable URLs, and disallowed schemes all fail closed.

Confidence gating works the same way: Scanner.run_modules() drops any finding below config/settings.yaml's min_confidence (default 0.6). The following modules are heuristic by design and sit below that threshold on purpose:

core/ssrf_guard.py — unsafe IP check

def _is_unsafe_ip(ip_str):
    ip = ipaddress.ip_address(ip_str)
    return (
        ip.is_private
        or ip.is_loopback
        or ip.is_link_local
        or ip.is_multicast
        or ip.is_reserved
        or ip.is_unspecified
    )
ModuleConfidenceWhy it's heuristic
idor0.50A differing response for a sequential ID is suggestive, not proof of an authorization flaw.
csrf0.55Absence of a recognized token field name doesn't rule out other CSRF defenses (e.g. SameSite cookies).
auth_bypass0.40Based on response-shape comparison, not a confirmed bypass.
business_logic_abuse0.50Value echoing alone is weak evidence of a real logic flaw.
rate_limit_bruteforce0.55Behavioral/statistical; can't rule out app-level controls like CAPTCHA.
file_upload_testing0.40Missing a client-side accept attribute is not itself a server-side control.

Everything else — misconfig, xss, sqli, open_redirect, cors_misconfig, path_traversal, ssrf, xxe, jwt_validation_weaknesses, insecure_deserialization, graphql_specific_testing, file_inclusion_indicator — scores at or above 0.6 and shows up by default. Treat every finding as a lead to verify manually, not a confirmed vulnerability.

Architecture

Scanning workflow

One HTTP chokepoint, one authorization gate, one confidence filter — every run follows the same pipeline whether it's scan, test, or exploit.

01
CLI entry
bugpilot_cli.py routes scan/crawl/recon/test/exploit
→
02
Scope & authorize
core/scope.py — allowlist, --authorize, or interactive y/N
→
03
SSRF-guarded HTTP
core/utils.py + core/ssrf_guard.py revalidate every redirect hop
→
04
Recon & crawl
core/recon.py, core/crawler.py build endpoint inventory
→
05
Module dispatch
core/plugin_manager.py runs enabled modules/ detectors
→
06
Confidence filter
drop findings below min_confidence (0.6 default)
→
07
Risk score & dedup
core/risk_scorer.py, core/validator.py
→
08
Report artifacts
core/reporter.py → report.md / findings.json / results.sarif

Installation

Quick start

1 — Clone & install
git clone https://github.com/imharshitaa/bugpilot.git
cd bugpilot
python3 -m venv venv
source venv/bin/activate
pip install -e .[test,demo]
2 — Try it safely against the bundled lab app
python -m labapp.app &
bugpilot scan http://127.0.0.1:5000 --authorize
3 — Command reference
bugpilot scan <url> [--authorize] [-export [path]]
bugpilot crawl <url> [-authorize] [-export [path]]
bugpilot recon <url> [-authorize] [-export [path]]
bugpilot test <url> [--authorize] [-export [path]]
bugpilot exploit <url> [--authorize] [-export [path]]
4 — Headless / CI mode
python3 main.py --headless \
  --targets http://127.0.0.1:5000/ \
  --authorize \
  --modules all \
  --formats json,sarif \
  --fail-on-findings
